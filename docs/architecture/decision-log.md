# Decision log: React + TypeScript migration

This log covers the migration defined in `READ THIS IMPORTANT FOR EVERY AI/DWDG_Semi_ERP_Refactoring_Master_Prompt.md` (the "master prompt"). Product decisions (D1 to D66) live in `.planning/DECISIONS.md` and stay authoritative for behaviour. This file records engineering decisions only.

Status values: **owner** = decided by the project owner, **engineering** = decided during the migration with the reason given, **open** = needs an answer.

| ID | Date | Decision | Alternatives considered | Reason | Status |
|---|---|---|---|---|---|
| M1 | 2026-10-15 | The migration source is `frontend/prototype/` only. `frontend/app/` (v1.1 workspace and the dwdg'ONE preview), `frontend/concepts/` and `backend/client/` are not migrated. They are archived to `bin/` after reference checks. | Migrate `frontend/app/` too; migrate both | The prototype is the current product (rounds D49 to D66). The other two frontends are earlier generations with different data models (`next-app/AUDIT.md` §0.2). | owner |
| M2 | 2026-10-15 | Stack: Vite + React + TypeScript, per the master prompt. The Next.js 15 plan in `next-app/` (wrap the legacy scripts unchanged) is superseded. Its Supabase schema is kept and moved to `database/`. | Continue the Next.js wrapper plan | The master prompt requires a real React + TS migration. A static SPA also fits the PRD's static hosting plan (`infrastructure_static`). Next.js server features are not needed because there is no custom server code. | owner |
| M3 | 2026-10-15 | Styling: full conversion to Tailwind CSS. The design tokens (`.planning/design/system/tokens.css`) remain CSS custom properties, because dark mode re-tunes rather than inverts them. Tailwind's theme points at those variables. | Keep the existing CSS files and use Tailwind only for new code | Owner's choice. Visual parity is still required and is checked against `qa/refactor-baseline/`. | owner |
| M4 | 2026-10-15 | Data goes straight to Supabase (PostgreSQL, Auth, RLS). There is no localStorage stage for workspace records. | localStorage first, Supabase later | Owner's choice. | owner |
| M5 | 2026-10-15 | No dedicated backend service. Supabase is the backend: Auth (Google, invite-only hook), PostgREST RPCs `load_workspace()` and `apply_changes()`, and RLS on every table. `backend/` holds no server code and documents this decision. | Fastify or Express API on a separate host | The master prompt says not to build a backend for appearance. The PRD (`infrastructure_functions`) says routine writes use policy-protected managed APIs, with no second general backend runtime. Every current action is a record write that RLS can authorise. | engineering |
| M6 | 2026-10-15 | Database design: the `next-app/supabase` schema (61 tables, each record kept whole in `doc json` with generated key columns for foreign keys, indexes and RLS). Moved to `database/` as is. | Fully typed columns per field; reuse the v0.3 SQL in `database/migrations` | The v0.3 SQL does not match the prototype's data model (`next-app/AUDIT.md` §6.4). The `doc` design keeps every record shape the screens rely on. Typed columns can be added per table later without touching the app. | engineering (carried over from approved Stage 2) |
| M7 | 2026-10-15 | Frontend state: one workspace store (`useSyncExternalStore`) holding the loaded workspace. Every user action runs as one transaction: Immer produces the next state and the list of patches, the patches become per-table upserts and deletes, and `apply_changes()` saves them atomically. On failure the store rolls back and shows the prototype's text "Could not save. Your changes are still here. Please try again." | Zustand or Redux; TanStack Query mutations per entity | 542 prototype actions mutate one in-memory store and then save. Immer keeps that logic readable, and its patches yield the exact changed rows. TanStack Query loads the workspace and refetches it. | engineering |
| M8 | 2026-10-15 | Routing: React Router with path URLs (`/projects/p-roadmap`) instead of hash URLs (`#/projects/p-roadmap`). Old hash links are redirected to the same path on load. Route shapes and page keys stay the same. | Keep hash routing | The PRD asks for stable entity URLs (`engineering-routing`), and Vercel serves an SPA rewrite. Redirecting keeps old links working. | engineering |
| M9 | 2026-10-15 | Sign-in: Google OAuth, invite-only, through the Supabase "before user created" hook. The prototype's demo persona picker is kept only when `VITE_DEMO_MODE=true`, together with an in-memory data adapter seeded from the prototype's demo data, for local development and automated parity tests. | Remove the picker | Carried over from the owner's approval of 12 Oct (next-app Q5). The PRD says the demo people stay out of production (next-app Q7). | owner (12 Oct) |
| M10 | 2026-10-15 | Per-device preferences (theme, language, look, collapsed sections, navigation group) stay in `localStorage`, as in the prototype. Only workspace records go to Supabase. | Store preferences in Supabase | These preferences belong to the device in the prototype. Moving them would change behaviour. | engineering |
| M11 | 2026-10-15 | Translation: the prototype's English-keyed dictionary (`core/i18n.js`, English to Bahasa Indonesia, `{name}` placeholders) moves unchanged into a typed `t()` helper. No i18n library. | i18next | Same behaviour, no new dependency, and the 1,600 entries are reused exactly. | engineering |
| M12 | 2026-10-15 | Fonts: Geist and Geist Mono are self-hosted through `@fontsource` packages instead of loaded from Google Fonts. | Keep the Google Fonts link | Same typeface and weights. The PRD asks for no runtime CDN dependency for operational essentials (`engineering-dependencies`, `engineering-assets`). | engineering |
| M13 | 2026-10-15 | Hosting: Vercel for the frontend (master prompt §3). This conflicts with owner decision **D3** (5 Oct: "Supabase + Cloudflare Pages", free tiers) and PRD `infrastructure_static`. The build is a plain static SPA, so either host works without code changes. A `vercel.json` is added, and the Cloudflare Pages settings are documented next to it. | Cloudflare Pages only | The master prompt names Vercel, but D3 is an earlier owner decision. Recorded as a conflict, not silently chosen. Vercel's Hobby plan is for non-commercial use, which needs checking for an organisation app. | **open**: owner picks the host before Phase 6 |
| M14 | 2026-10-15 | Tests: Vitest + Testing Library + happy-dom for units and components. Playwright (`playwright-core` with the installed Chrome) for end-to-end and visual parity against `qa/refactor-baseline/`. The 377 legacy `node --test` tests cover code that is archived (frontend/app, backend/client) or rewritten (prototype core). They are archived with that code and replaced feature by feature. | Keep `node --test` | Vitest runs TypeScript and JSX natively under Vite. Playwright is needed for real rendering checks. | engineering |
| M15 | 2026-10-15 | Repository layout follows master prompt §4: `frontend/` (the React app at the folder root), `backend/` (docs only, see M5), `database/`, `docs/`, `scripts/`, `bin/` (archive only). Current `bin/` generator scripts move to `scripts/`. `.planning/`, `PROJECT_REFERENCES/`, `READ THIS IMPORTANT FOR EVERY AI/`, `qa/` and `backups/` stay where they are (AGENTS.md says they did not move; they are project records, not code). | Move them under `docs/` | They are referenced by many existing documents and tools. Moving them breaks those paths and is not needed for the migration. | engineering |
| M16 | 2026-10-15 | `frontend/prototype/` stays runnable until every feature passes parity. It is then archived to `bin/` with a manifest entry. | Archive it now | It is the behavioural and visual reference for the parity checks. | engineering |
| M17 | 2026-10-15 | The three looks (Comfortable, Compact, Simple), light/dark/system theme and English/Indonesian are all migrated. They are owner decisions D52 to D57 and D63, so they are features, not legacy. | Ship Comfortable only | Master prompt §2: do not remove features. | engineering |
