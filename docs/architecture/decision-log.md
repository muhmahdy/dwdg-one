Status values: **owner** = decided by the project owner, **engineering** = decided during the migration with the reason given, **open** = needs an answer.

| M30 | 2026-10-17 | The server applies a table's rule to a save exactly as PostgreSQL applies row level security to the app's own save path (`insert ... on conflict do update`, through `apply_changes`): the record as it will be must pass the write rule AND the read rule, new or not, and a stored record that is changed or deleted must be one the person can both read and write. Rules for `mcit`, `ee` and `cons` are in `server/src/lib/policy/`; the parity gate for them also runs over the 41 demo people and through the whole server over four real division projects. | Treat write as independent of read (the first version); compare only plain statements | The app never issues a plain insert or update, only the upsert; the parity test must exercise the path that runs. | engineering |
| M31 | 2026-10-17 | Operations (stage H6). (1) Access changes are not moved to dedicated `/api/access/*` action routes: the accounts screens save through `/api/changes` like everything else, and the hub's policies and people guard already enforce the spec's matrix. Instead the server writes every change of authority (a person's role, division, admin, board or status; added or removed people; writes to the account tables) to `audit_log` with who did it, and the Admin and the President read it at `GET /api/audit`. (2) Rate limits live in the server, in memory by default, behind a two-method interface so a shared store (Upstash) can replace it; per address only refused tokens count. (3) The scheduled job is `GET /api/cron/ping` with `CRON_SECRET`, called by GitHub Actions twice a week (Vercel Hobby cron is daily and limited). (4) Backups: seven projects, HR and FnL never written without `BACKUP_ENCRYPTION_KEY`, every dump encrypted when the key is set, weekly workflow with 56 days of retention as a first copy. (5) The browser app's headers, including a Content-Security-Policy, are in `frontend/vercel.json`. | (1) Rewrite each accounts action as a server route; (2) Upstash from the start; (3) Vercel Cron; (4) one backup of everything | (1) The accounts feature is built on change sets and the database already refuses what the matrix forbids; a rewrite would add risk without adding enforcement. (2) to (5) need no new service before the projects exist. | engineering |

| M33 | 2026-10-17 | Stage H8, the tool. `scripts/database/move-data.mjs` moves a workspace to the hub and the six division projects (`--target hub|spoke:<slug>|a list|all|legacy`): a check with no network, a look at the projects with nothing written, then a move that writes one project per transaction, reads it back and compares every row with its key order. | M35 | 2026-10-17 | The server runs as one Node process in one container on a small host (Render, Railway, Fly, or an own server), not as serverless functions. `server/src/main.ts` is the production entry (environment in, all interfaces, `GET /api/health` for the host, clean stop on SIGTERM, exit 1 on an escaped error so the host restarts it); `server/Dockerfile` builds an image of only the server's runtime dependencies and sources (no build step: Node 24 runs the TypeScript); `.dockerignore` lists what may enter the build and nothing else.
