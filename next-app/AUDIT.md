# AUDIT — DWDG'ONE → Next.js + Supabase migration (Stage 0)

Audit date: 12 Oct 2026. Read-only: no original file was modified (see §10 for the one pre-existing change in git).
Method: read the sources and docs, ran `npm test`, and loaded the prototype in happy-dom to dump its live data shape. Numbers below were measured, not estimated. Where I did not audit something in depth, it says so.

---

## 0. Read this first — findings that change the plan

1. **There is no backend to migrate.** No HTTP endpoint, server, or `fetch()` call exists anywhere in the project. "Backend" is (a) `backend/client/shared-backend.mjs`, a browser-side Supabase wrapper that the current UI does not use, and (b) SQL migrations in `database/`. So Stage 3's "backend endpoints → Route Handlers" has nothing to map one-to-one; the Route Handlers would be **new** code.
2. **There are three frontends, not one.** `frontend/prototype/` (the current, actively developed product, D49–D66), `frontend/app/` (Vite app: older "v1.1 workspace" plus a "dwdg-one preview"), and `frontend/concepts/` (static design pages). They have different data models and different stores. I need you to say which is the migration source (§11, Q1).
3. **The existing SQL schema does not match the prototype's data model.** Different division codes and names, different role system, UUID vs readable string IDs, and no tables for most prototype features (offers, operations/routines, programs, pins, availability, hand-ins, EE/Consulting/FnL/MCIT/HR workflows, account lifecycle, etc.). Details in §6.4. Rule 3 ("keep table and column names the same as the old data") cannot be satisfied by reusing the SQL that exists; Stage 2 would be a new schema.
4. **The prototype is not structured as modules.** 21 classic `<script>` files (+ `qa.js` only with `?qa`) share one global scope, load order matters, functions are redefined by later files ("last script loaded wins"), and runtime code **re-assigns** `save`, `render`, `renderLayer`, `toast` and `showToast` (persistence.js, ui-polish.js, qa.js). Every screen builds HTML strings and re-renders the whole `#app` with `innerHTML`. This is the main risk for "identical markup and behavior" in React (§9).
5. **Routing is hash-based** (`#/work`, `#/projects/<id>`). Hash routes are invisible to the server, so "keep the same URLs / one route per page" needs a decision (§11, Q3).
6. **Auth is simulated** in the prototype (pick a demo persona; session in localStorage). Real Google sign-in exists only in the unused `shared-backend.mjs` + SQL hook.
7. The prototype's CSS depends on files **outside** `frontend/`: `.planning/design/system/tokens.css`, `components.css`, `.planning/brand/*.svg`, `.planning/design/people/*.jpg` (26 image files in `design/people/`, photos supplied by the owner), plus Google Fonts (Geist) over the network.

**Runtime rebinding (important):** `DBCommit.run()` temporarily replaces the globals `save`, `render`, `renderLayer`, `toast`, `showToast` to defer rendering until the one `localStorage` write succeeds, and rolls back `db`, `ui`, `UNDO` on failure. At `DOMContentLoaded` app.js also overrides `toast`, `MENUS.new/more`, `paintHist`, `runUndo`, `runRedo`, `opsNav`, leaving "interim" versions in work.js as dead code. `ACT` handlers are wrapped by `DBCommit.wrapActions`. Duplicate page keys (`updates`, `projects`, `work`) are re-assigned by later scripts; the last one wins.

**Non-determinism to preserve or fix consciously:** `uid()` uses `Date.now()` + `Math.random()`; `nowStamp()`/`nowMin()` use the real clock, while "today" is fixed to `2026-10-06` (`window.DEMO.today`).

**Other browser features:** WebGL shader art for project/program/operation/resource pictures (plan.js; 20 styles, one shared context), `matchMedia`, `visualViewport`, `getBoundingClientRect` for popup placement, `document.write` for the QA script, a `file://`-friendly design (no modules).

## 9. Migration risks (technical, specific)

1. **String-template rendering.** Each page returns an HTML string; the shell re-renders `#app` entirely and then restores scroll/focus by hand. To keep the markup byte-identical, the safest faithful port renders those strings (via `dangerouslySetInnerHTML` or a thin imperative host), not hand-written JSX. Rewriting 12k lines of templates as JSX would be a redesign. Needs your decision (Q4).
2. **Global scope + redefinition + runtime rebinding** (§4.1). ES modules cannot reassign imported bindings; `DBCommit`, `ui-polish`, `qa` need a restructure (a shared mutable context object). That is behavior-preserving but not mechanical.
3. **Hash router vs App Router** (Q3). Server components cannot read the hash; every prototype page would be a client component under one route unless URLs change.
4. **Hydration.** Output depends on `Date.now()`, `Math.random()`, `localStorage`, `matchMedia`, `innerWidth`; these must run only on the client.
5. **Load-order dependencies** (21 scripts; `schedule.js` last starts the app; later files override earlier definitions).
6. **Security model change.** Today all rules are client-side with simulated identity. With Supabase, rules must also be enforced by RLS; behaviors the UI allows implicitly (e.g. the persona switcher, `session.preview`, admin flag edits) have no server equivalent and must be redefined (Q5).
7. **Data model gap** (§6.4): the biggest piece of work in Stage 2.
8. **Tests** (§2): 377 tests assume happy-dom + `node:test`; they won't run unchanged under Next.
