# DWDG’ONE UII — operations research and decision baseline

Research checked **3 October 2026**. These are planning inputs for a real future launch. No vendor account was created, paid plan purchased, production migration run, or service published during this work. Prices/quotas can change and must be rechecked against the actual account before adoption.

## Confirmed constraints versus editable proposals

The latest user decision is an operating target of **Rp35,000/month where feasible**, with a **hard maximum of Rp50,000/month**. This supersedes the earlier near-Rp0 preference. There is no requirement to spend up to the target. The user also confirmed roughly **40 members or more** and **no existing organization domain or shared Drive account**. Keep free core services where they work, and prioritize any permitted small spend toward independent recovery/storage rather than unnecessary extras. Include recurring charges, annual costs amortized monthly, taxes and card/payment fees in the ceiling; actual annual upfront payment needs separate approval. No UII Workspace Shared Drive, expanded storage, SMTP, server or subdomain entitlement is assumed. The product name is **DWDG’ONE**, Universitas Islam Indonesia.

Capacity planning is harmonized at **60 accounts/invitations, 40 monthly active members and 15 concurrent sessions**, with **100 members/25 concurrent** as a proposed stress scenario. These are workload assumptions, not confirmed headcount or a performance result. The operational data estimate is 5,000 tasks/year and 200 linked external resources. **Default free V1 has zero native binary uploads**: native notes, folders and external document/app links come first. An optional future sizing scenario is 200 uploaded files averaging 1 MB, only if that capability is separately adopted. No video hosting or full external-Drive mirroring.

## Proposed initial stack and truthful operating boundary

The first candidate is a static Vite/vanilla JavaScript frontend on a free Cloudflare Pages subdomain, Supabase Free for relational data/Auth, native notes/folders/link resources, invite-only Google OAuth, and in-app updates. Private binary uploads remain deferred unless explicitly adopted. Primary Google login can avoid a mandatory transactional-email dependency; application invitations are admin-created, restricted to approved identities, with invitation links distributed through a separately authorized organizational channel. No domain purchase or SMTP subscription is required by default.

The public project URL/publishable key can be present in the frontend, with server-enforced row/field permissions. Secrets, backup credentials, SMTP keys and privileged DB/service credentials stay outside the client. The static deployment is the web frontend; managed database/Auth/Storage are separate dependencies. A client sandbox flag is insufficient isolation.

This core fits the current budget, with a small optional independent archive charge after actual eligibility/billing checks. A real small launch requires actual multi-user permissions, persistence, conflicts, export/restore and rendering evidence. Free hosting does not create an uptime SLA. A polished interface cannot substitute for independent recovery, named custodians, a quota response plan or student-term succession.

## Backup mechanism: what is proposed and what is still missing

There is no existing backup automation or institutional archive assumed. Candidate budget-fit mechanism: a restricted private scheduled CI job exports logical/portable DB records, native note contents and the external-link manifest, builds a checksum manifest, encrypts the package and uploads to an approved private offsite destination. **It does not copy or restore external-provider document bytes**; resources need a separate owner/archive procedure for critical evidence. Optional future native uploads add new/changed blob copies before that capability can ship. A private R2 Standard archive is a useful candidate because bounded small storage can fit the permitted budget and object credentials avoid an unattended consumer-Drive OAuth dependency. Actual account/payment eligibility, quotas, rounding, fees and billing controls remain Open; nothing was provisioned. A newly arranged restricted custodian Drive folder with individual access is the alternative. Repository, CI logs and ordinary artifacts must contain no raw member records or decrypted archives.

Drive automation requires its own carefully scoped API authorization. Login-only OAuth and Drive upload authorization differ; external Google apps in Testing can receive seven-day refresh tokens for non-profile scopes. Revocation or expiry must produce visible backup failure and operator reauthorization, rather than an empty green run. No consumer service-account storage or institutional delegation is assumed. [Google OAuth token documentation](https://developers.google.com/identity/protocols/oauth2#expiration)

If automation cannot yet be configured/tested, the transparent temporary fallback is a named custodian performing a daily encrypted portable record/native-note/link export at a documented time. This has real volunteer effort and can miss days. Crucial finance/recruitment reliance remains blocked if current backup age and restore evidence cannot substantiate the accepted recovery goal or external evidence ownership is inadequate. A desktop folder or scheduled export button is not independent recovery.

Initial proposed retention is seven daily, four weekly and three monthly complete **app-owned record/note/link** generations, with privacy exceptions and actual storage sizing. A 20 MB daily compressed record export transfers approximately 600 MB per 30 days before member API traffic. If binary upload is later adopted, incremental blob retention avoids copying every attachment nightly, but each generation must identify its required immutable offsite objects; deleting a referenced object makes that generation incomplete.

Proposed recovery goals are at most 24 hours of missing acknowledged work and recovery within eight **staffed working hours** after recognition. These are goals, not a guarantee; weekend/exam availability must be agreed. Demonstrate restoration into an isolated restricted destination, verify entity counts, relations, auth/person mapping, permissions and native note contents, then exercise login/task/approval/provider-link journeys. Clearly state that external document bytes remain outside restored scope. Optional uploads require additional blob checksum/retrieval restoration. Record achieved duration and loss interval. Repeat quarterly and at term handover.

Actual invoices may still be Rp0 when eligible allowances cover everything; there is no minimum spend. Volunteer time, existing member devices/internet and unverified university support are separately disclosed operating effort rather than vendor charges.

**Example A — free core plus a small archive.** Pages/subdomain, Supabase Free and primary OAuth without mandatory email have an illustrative $0 core charge. Add a **Rp2,000 unquoted tax/card/payment allowance** and **Rp10,000 unspent contingency reserve**: planned envelope **Rp14,475**, below target and ceiling. ## Alternative architecture and why it is not the first candidate

Workers+D1 is a possible free-cost alternative; checked D1 includes five million read rows/day, 100,000 writes/day and 5 GB total storage at the account level. Daily/size limits can stop queries and indexes affect usage. Its attractive storage/transfer model still requires a secure application API, Google identity/session handling, scoped authorization, file access and recovery. It cannot be treated as the same finished managed identity/RLS backend. Defer switching unless the inactivity/reliability tradeoff warrants the extra maintenance and migration work. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

A student-operated VPS adds patching, DB/mail/recovery duties and succession risk. Do not count donated hardware as a zero-effort service. V1 avoids microservices, a full accounting engine, automated payments/signatures, public SaaS tenancy and collaborative offline document editing.

## Data and audit architecture supplied to the PRD

The operations JSON contains a named entity dictionary for organizational structure/terms, people/auth links/membership/roles, invitation/capability, projects/participants/tasks/assignees/milestones/dependencies/blockers, resources/folders/links/notes/file versions/associations/comments/decisions, meetings/attendees/availability, notifications/activity, all six divisions’ domain records, approvals/recorded payments, audit and export/import jobs. It specifies IDs, fields, null/history handling, validation, relations and scope. It is a proposed schema baseline rather than a mandate to create a table per view.

Production audit actors derive from verified server identity, never a client-claimed user. Events retain organization/affected workspace scope, action, entity ID/type, sanitized title snapshot, correlation ID, server timestamp, revision and authorized redacted old/new differences. Moves/deletions preserve safe scope history; restricted HR/finance data and secrets never leak through Changes, counts, search or exports. Workspace Changes is a permission-filtered view; device-local PRD editing history is a separate honest local feature.

Existing local records and IndexedDB files must be exported and classified before migration. CSV reports are human-readable filtered exports; JSON is a versioned relation-preserving bundle; resource manifests state native-note contents and external-link scope. Legacy file bytes remain in a verified legacy archive until an adopted provider/upload transition covers them, without false migrated status. Optional file bundles state inclusion/missing bytes. Restore is an authorized dry-run/reconciliation workflow with destination backup, not silent overwrite. Unknown dates/owners remain unresolved, and no existing records are reseeded over.
